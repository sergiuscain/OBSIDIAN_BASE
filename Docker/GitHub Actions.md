### Что это
**GitHub Actions** — это встроенная в GitHub платформа для автоматизации рабочих процессов (workflow) прямо в вашем репозитории. С её помощью можно настроить сборку, тестирование, развёртывание кода, а ещё — автоматизировать рутину вроде проверки кода, отправки уведомлений или резервного копирования. Часто её используют для реализации CI/CD (непрерывной интеграции и доставки). 
### РеализацияCI
1) Создаем папку `.github/workflows` в корне репозитория 
2) Создаем файл формата `.yml`, например: `deploy.yml`
	Пример файла:
```yml
on: push

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker login -u ${{ secrets.DOCKERHUB_USERNAME }} -p ${{ secrets.DOCKERHUB_TOKEN }}
      - run: docker build -t ironprogrammer/reviews-service:latest ./reviews-service
      - run: docker push ironprogrammer/reviews-service:latest
```
- `on` задает, когда запускать конвейер. Здесь на каждый `git push` в репозиторий.
- `jobs` это список задач конвейера. У нас одна задача build.
- `runs-on` говорит, на какой машине выполнять задачу. GitHub выдает чистую виртуалку, тут с Ubuntu.
- `steps` это шаги задачи, они идут по порядку сверху вниз.
- `uses` подключает готовый экшен, например `actions/checkout`, который забирает код репозитория. (готовый набор действий называется actions. Все actions можно посмотреть на [GitHub Marketplace](https://github.com/marketplace?type=actions)  
- `run` выполняет команду в терминале виртуалки, как будто ты сам ее набрал.
### Секреты в workflows

Логин и пароль от docker – это секреты. Их мы не пишем в воркфлоу. 
Их кладут в GitHub Secrets, отдельное защищенное хранилище репозитория. GitHub шифрует значения и прячет их в логах, даже если случайно вывести секрет на экран, в логе будут звездочки.

Секреты живут в настройках репозитория. Открываешь `Settings`, раздел `Secrets and variables`, вкладку `Actions`, жмешь `New repository secret` и задаешь имя и значение. Значение потом не посмотреть, только заменить на новое.

Например, для нашего конвейера нужно два секрета. Заводишь `DOCKERHUB_USERNAME` и в значение вписываешь свой логин на Docker Hub. Потом `DOCKERHUB_TOKEN`, а в значение токен доступа Docker Hub. Все, теперь воркфлоу залогинится этими секретами и сам запушит образ.

В файле секрет вставляют по имени через `${{ secrets.ИМЯ }}`. Реального пароля в файле нет, есть только ссылка на секрет.

### РеализацияCD

### Создание ssh ключа
Для входа на сервер мы будет использовать ssh-ключ.
1) Создаем пару ключей:
```cmd
ssh-keygen -t ed25519 -C "deploy"
```
Флаг `-t ed25519` задает тип ключа, это современный и короткий вариант. Флаг `-C` добавляет метку-комментарий, чтобы потом вспомнить, для чего ключ. На вопрос про пароль к самому ключу жми Enter и оставь его пустым. Если задать пароль, робот не сможет войти без ручного ввода, а нам нужно, чтобы все шло само.

Получаются два файла. Приватный `id_ed25519` и публичный `id_ed25519.pub` с расширением `.pub`. Дальше их разносят по разным местам:

- Содержимое публичного `.pub` дописывают на сервере в файл `~/.ssh/authorized_keys`. Это список ключей, которым сервер доверяет. Публичный ключ не секретный, его можно спокойно копировать.
- Содержимое приватного файла целиком, вместе со строками `BEGIN` и `END`, кладут в GitHub Secret `SSH_PRIVATE_KEY`. Приватный ключ секретный, его нельзя писать в файл-воркфлоу, только в секрет.
### Как положить публичный ключ на сервер
1. На своей машине посмотри публичный ключ командой `cat ~/.ssh/id_ed25519.pub` и скопируй всю строку, она начинается с `ssh-ed25519`.
2. Зайди на сервер по паролю командой `ssh root@адрес-сервера`. Пароль берешь у своего хостинга.
3. На сервере создай папку для ключей и дай ей права командой `mkdir -p ~/.ssh && chmod 700 ~/.ssh`.
4. Открой редактором nano файл доверенных ключей командой `nano ~/.ssh/authorized_keys`. В этот файл сервер смотрит, решая, кого пускать. Вставь строку из первого шага на новую строку, сохрани сочетанием `Ctrl+O` и `Enter`, потом выйди через `Ctrl+X`.
5. Поставь права на файл ключей командой `chmod 600 ~/.ssh/authorized_keys`, чтобы доступ к нему был только у тебя. Зачем это важно, разберем сразу после шагов.
6. Выйди командой `exit` и проверь вход по ключу командой `ssh -i ~/.ssh/id_ed25519 root@адрес-сервера`. Если сервер пустил без пароля, ключ на месте.
В шагах выше была команда `chmod`. Она меняет права доступа, то есть решает, кому можно читать и менять файл или папку. Права записывают тремя цифрами по порядку, для тебя как владельца, для твоей группы и для всех остальных на сервере. Чем больше цифра, тем больше разрешено. 7 – это полный доступ, 6 – это только чтение и запись, 0 – это запрет.

Отсюда наши числа. Права `700` на папке `.ssh` дают полный доступ тебе и запрещают всем остальным. Права `600` на файле `authorized_keys` разрешают тебе читать и писать, а остальным ничего. Смысл один. К ключам не должен подобраться никто, кроме владельца.

Приватный ключ на сервер не кладут никогда. Он идет только в GitHub Secret `SSH_PRIVATE_KEY`, чтобы робот мог им представиться при входе.

### Какие секреты нужны для деплоя
Кроме ключа деплою нужны адрес сервера и имя пользователя. Их тоже держат в GitHub Secrets. Для нашего конвейера полный набор такой:

- `DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN`, логин и токен от registry.
- `SERVER_HOST`, адрес сервера.
- `SERVER_USER`, пользователь на сервере.
- `SSH_PRIVATE_KEY`, приватный ключ для входа.
### Деплой выносим в отдельный job
Сборку и отправку образа делает job `build`, это CI. Деплой – это уже другая задача, CD, поэтому его выносят в отдельный job `deploy`. Он заходит на сервер по `ssh` и обновляет проект. Вход берет готовый экшен, он сам подключается ключом из секрета:
```yml
deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - name: Deploy
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          key: ${{ secrets.SSH_PRIVATE_KEY }}
          script: docker compose pull && docker compose up -d
```
Строка `needs: build` тут главная. Она говорит, что `deploy` стартует только после того, как `build` успешно закончился. Без нее оба job запустятся сразу и параллельно, и деплой может уйти раньше, чем образ окажется в registry.

У экшена в блоке `with` четыре поля. `host` и `username` это адрес сервера и пользователь, `key` это приватный ssh-ключ, все три берутся из секретов. `script` это команды, которые выполнятся уже на сервере.

На сервере `docker compose pull` забирает свежий образ из registry, а `docker compose up -d` перезапускает проект с новым образом. При этом на сервере уже должны стоять Docker и файл `docker-compose.yml` ([[Docker Compose]]), где у приложения указан образ из registry через `image`.  

### docker-compose.yml на сервере
На сервере он лежит в той папке, куда ssh заходит по умолчанию, там же выполняется шаг деплоя, поэтому переходить куда-то отдельной командой не нужно:
```yml
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: reviews
    volumes:
      - pg-data:/var/lib/postgresql/data
    healthcheck:
      # Проверяем, что база готова принимать подключения
      test: ["CMD-SHELL", "pg_isready -U postgres -d reviews"]
      interval: 5s
      timeout: 3s
      retries: 5

  api:
    image: ironprogrammer/reviews-service:latest
    ports:
      - "80:8080"
    environment:
      ConnectionStrings__Postgres: ${ConnectionStrings__Postgres}
    depends_on:
      db:
        # Ждем не просто старта контейнера, а готовности базы (healthcheck прошел)
        condition: service_healthy

volumes:
  pg-data:
```
Главная строка тут `image: ironprogrammer/reviews-service:latest` у сервиса `api`
Это имя обязано совпадать в трех местах, иначе деплой не сработает:
- В воркфлоу при сборке, `docker build -t ironprogrammer/reviews-service:latest`.
- В воркфлоу при отправке, `docker push ironprogrammer/reviews-service:latest`.
- В `docker-compose.yml` на сервере, `image: ironprogrammer/reviews-service:latest`.
- В качестве образа можно использовать не только DockerHub:
- `ghcr.io/sergiuscain/inventoryservice:latest` - пример ссылки на образ из GitHub (ghcr.io)

# Полный алгоритм публикации
Настройка один раз:
1. Завести аккаунт в registry, например Docker Hub, и получить токен доступа.
2. Подготовить сервер, поставить Docker и положить `docker-compose.yml` с образом из registry через `image`.
3. Сделать пару ssh-ключей через `ssh-keygen` и добавить публичный ключ на сервер в `~/.ssh/authorized_keys`.
4. Добавить в GitHub Secrets репозитория `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`, `SERVER_HOST`, `SERVER_USER`, `SSH_PRIVATE_KEY`.
5. Написать воркфлоу `.github/workflows/deploy.yml` со сборкой, отправкой и деплоем.

Дальше на каждый `git push` робот делает все сам:
1. Забирает код через `checkout`.
2. Логинится в registry секретами `DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN`.
3. Собирает образ через `docker build`.
4. Отправляет образ в registry через `docker push`.
5. Заходит на сервер по `ssh` ключом из `SSH_PRIVATE_KEY`.
6. Выполняет `docker compose pull` и `docker compose up -d`.

От правки в коде до обновленного приложения на проде, без единой ручной команды.
