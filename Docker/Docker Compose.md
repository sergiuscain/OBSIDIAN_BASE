Docker Compose позволяет описать весь проект в одном файле `docker-compose.yml`. В нем перечислены все сервисы, их настройки, сеть и volume. А запускается все одной командой:
```
docker compose up
```
Compose сам создаст сеть, поднимет базу, соберет и запустит приложение, причем в правильном порядке. Остановить и убрать все тоже одной командой:
```
docker compose down
```


В этом уроке разберем docker-compose.yml целиком. Как устроен файл, из чего состоит, какие настройки бывают и как сервисы находят друг друга. Все на примере нашего проекта из прошлых уроков, приложения и базы.

### Тот же проект, но одним файлом

В прошлом модуле мы поднимали базу и приложение отдельными командами. Вот тот же проект, описанный в docker-compose.yml:

```
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_PASSWORD: secret

  app:
    build: .
```

### services

`services` – это главный раздел файла. Внутри перечислены все контейнеры проекта, каждый тут называется сервисом. У нас два сервиса, `db` и `app`. Имя сервиса ты придумываешь сам, и по этому имени к сервису обращаются соседи, как раньше по `--name`.

### image против build

У сервиса `db` стоит `image: postgres:17-alpine`. Это значит взять готовый образ из реестра, как раньше делал `docker run postgres:17-alpine`. У сервиса `app` стоит `build: .`, это значит собрать образ из `Dockerfile` в текущей папке, как раньше делал `docker build -t myapp .`. Одному сервису образ дают готовый через `image`, другому собирают через `build`, один из двух.

### Отступы решают все

В YAML отступы – это не украшение, а смысл. Именно по ним compose понимает вложенность, что внутри чего лежит. Отступ – это ровно два пробела на каждый уровень. Только пробелы, табы использовать нельзя, с табами файл не прочитается:

```
services:
  db:
    image: postgres:17-alpine
```

Смотри. `db` вложен в `services` на два пробела. `image` вложен в `db` еще на два, итого четыре. Сдвинешь строку не туда, и compose поймет структуру неправильно.

### ports

Пока база видна только приложению внутри Compose. Чтобы подключиться к ней снаружи, например из DBeaver, порт пробрасывают. Как раньше флаг `-p`, в Compose это раздел `ports`:

```
db:
  image: postgres:17-alpine
  ports:
    - "5432:5432"
```

Слева порт на твоем компьютере, справа порт внутри контейнера, как в `-p 5432:5432`.

### environment

Настройки контейнеру передают через `environment`, как раньше флагом `-e`. У базы так задают пароль:

```
db:
  environment:
    POSTGRES_PASSWORD: secret
```

### volumes

Чтобы данные базы не пропали при пересоздании, их держат в volume, как в прошлом модуле. Volume подключают у сервиса и объявляют в разделе `volumes` верхнего уровня:

```
services:
  db:
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

### Сеть создается сама

В прошлом модуле, чтобы контейнеры увидели друг друга, мы вручную делали `docker network create` и запускали с `--network`. В Compose этого не надо. Compose сам создает общую сеть проекта и подключает к ней все сервисы. Приложение обращается к базе по имени сервиса, `db`, а не по `localhost`.

### Главное из урока

==🟠Файл docker-compose.yml описывает проект в разделе `services`, каждый контейнер – это сервис со своим именем. Готовый образ задают через `image`, свой собирают через `build`. Отступы задают вложенность, ровно два пробела, без табов. Порт пробрасывают через `ports`, настройки передают через `environment`, данные хранят в `volumes`. Общую сеть Compose создает сам, и сервисы находят друг друга по имени, без `docker network create` и `--network`.== 



### depends_on
```
services:
  db:
    image: postgres:17-alpine
    ports:
      - "5432:5432"
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5

  app:
    build: .
    depends_on:
      db:
        condition: service_healthy

volumes:
  pgdata:
```
В примере выше в приложении app прописаны условия через depends_on. 
db:
        condition: service_healthy - означает, что приложение db должно быть запущенно до запуска app. 

==🟠**Таким образом depends_on нужен, что бы установить порядок запуска сервисов.**==


### Запуск

Поднять весь проект из compose-файла одной командой:

```
docker compose up
```

Compose создаст сеть, поднимет базу, соберет и запустит приложение. Логи всех сервисов пойдут прямо в терминал. Чтобы запустить в фоне и освободить терминал, добавляют флаг `-d`, как у `docker run`:

```
docker compose up -d
```

### Пересборка

Если ты поменял код приложения, образ нужно собрать заново. Обычный `up` возьмет старый собранный образ. Чтобы Compose пересобрал его перед запуском, добавляют флаг `--build`:

```
docker compose up --build
```

### Остановить проект

Остановить контейнеры, не удаляя их:

```
docker compose stop
```

Контейнеры и сеть остаются на месте, просто выключены. Поднять обратно тем же составом можно быстро:

```
docker compose start
```

`stop` удобен, когда надо приостановить работу и скоро вернуться, не пересобирая и не пересоздавая контейнеры.

### Убрать проект

Остановить и удалить контейнеры и сеть проекта одной командой:

```
docker compose down
```

В отличие от `stop`, `down` удаляет контейнеры и сеть. Volume с данными при этом остается, поэтому база не потеряется.

### Посмотреть, что запущено

Список сервисов проекта и их состояние показывает одна команда, а логи другая:

```
docker compose ps
docker compose logs
```

### Главное из урока

`docker compose up` поднимает весь проект, флаг `-d` уводит его в фон, `--build` пересобирает образ перед запуском. `docker compose stop` останавливает контейнеры, не удаляя их, а `docker compose start` поднимает их обратно. `docker compose down` останавливает и убирает контейнеры и сеть, но volume с данными остается. Состояние смотрят через `docker compose ps`, логи через `docker compose logs`.
